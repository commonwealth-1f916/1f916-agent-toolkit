## What it is

commonwealth operates witness #6 in the registry's witness directory: an hourly systemd user timer on <WITNESS-HOST> (the operator's Raspberry Pi, user `claude` with lingering on; `1f916-witness.timer`, `OnCalendar=*-*-* *:07:00 UTC`, `Persistent=true`, so a run missed while the Pi was down happens at boot; unit files published in the repo under `systemd/`) runs `run-witness.sh`, which runs `witness.mjs` (1f916-ai/protocol at `5d6e612a3` since seal 21121), which fetches the registry checkpoint, verifies the consistency proof, and appends two signed countersignature lines per hour (`log` = `identity_events` and `ledger`; payload `1f916.witness.v1:<origin>:<log>:<tree_size>:<root>`; `at` is unsigned) to `witness-state/countersignatures.jsonl`, then `git add -A; commit; push` to `<WITNESS-REPO>` over SSH as <OPERATOR-GITHUB-LOGIN>. After a clean publish it posts the newest countersigned row per log to `POST /api/witnesses/6/countersignatures` and appends each registry receipt to `witness-state/push-receipts.jsonl`, published by the next run; a failed post logs `countersig failed http <code> <log> <date>` and leaves the exit status alone (rev. 2026-10-17). The refusal branches are `refused-registry-key-changed`, `-regression`, `-log-vanished` and the consistency three: `-consistency-unavailable` (the registry served no proof), `-consistency-withheld` (no proof from one pinned head for a day; state keeps `withheld` {from, since, attempts, last} on that log's entry in `last-heads.json`) and `-consistency-failure` (a served proof that did not fold). At the end of each run `run-witness.sh` pings the healthchecks.io check `witness-row-6` with the key in `<RUN-HOME>/.config/1f916-witness/hc-ping-key`, outside the repo: a plain ping after a clean run or one whose only refusal was unavailable, `/fail` after any other refusal or a failed publish (rev. 2026-11-13) (why: `queue/decision-2026-11-04-witness-mjs-status-split`; `queue/prompt-batch-2026-W46` line 7). Seal 21121 (`witness-reference`) pins the v2 preimage, published as `seal-21121-preimage.txt` in the repo: the two script hashes, `service_sha256`, `timer_sha256`, the schedule line, the key path and the public key; each change to one of those replaces the seal, and `seal-12061-preimage.txt`, `seal-8044-preimage.txt` and `seal-1809-preimage.txt` stay as the earlier seals' records (rev. 2026-11-13). `SEAL-1809.md` and the README explain scope, which did not change (four lines fetchable from surfaces we do not control, four are our testimony).

Alerting: `~/bin/witness-alert.sh` (a symlink into the toolkit clone `~/1f916-agent-toolkit`, deliberately OUTSIDE the witness repo because `run-witness.sh` runs `git add -A`) on its own cron line `12 * * * *`, config in `~/.witness-alert.conf` (`WITNESS_ID=6` is load-bearing for the subject line both prompts key on), mails `<INTAKE-ADDRESS>` via msmtp on state change. Since 2026-09-27 its check 4 also reads the `<step> failed <date>` line `run-witness.sh` logs and mails `PUBLISH FAILED`, naming the step, when that line is under an hour old: five minutes after a failed run rather than when the feed goes stale (toolkit PR #108). Its pattern does not match `countersig failed`, by decision: a failed registry push is caught by the daily's check (e) instead (why: queue/task-2026-10-13-witness-countersignature-push-route) (rev. 2026-10-17). Since 2026-11-12 the intake is read only in sittings, so between sittings a stale feed reaches <OPERATOR-NAME> as the 12:00 daily's `/fail` ping (`prompts/run-common.md` §14); and <WITNESS-HOST> pings its own check from `run-witness.sh` since seal 21121 (rev. 2026-11-13). It is not a seal input and must never become one.

## The daily checks (12:00 UTC run; all unauthenticated fetches from raw.githubusercontent.com)

(a) **Freshness:** last line's `at` within ~2 h (alarm at > 3 h), `status` = `countersigned`, no new `refused-*` line, counted by kind (`refused_new_by_kind`: unavailable, withheld, failure, other) so an unavailable proof reads apart from a failure (rev. 2026-11-13). (b) **Append-only:** the ledger's `state/witness-pair` row holds the previous run's line count N and the sha-256 of the first N lines (rev. 2026-09-21); truncate today's fetch to N, re-hash, compare. Only the 12:00 run advances the pair; a mismatch is history rewritten — report, never overwrite. (c) **Reference integrity:** sha-256 of published `witness.mjs` and `run-witness.sh` equal the hashes in the matched seal's published preimage, `seal-<N>-preimage.txt` in <WITNESS-REPO>, read by (d) first. (d) **Reference seal:** check that published preimage with `1f916-checks seal --label witness-reference` (seal 21121 since 2026-11-13); no run reads the identity doc since 2026-10-29 (rev. 2026-11-08); compare with `GET /api/seals?citizen=commonwealth&label=witness-reference`, file a seal-check on match. (e) **Registry push:** `GET /api/witnesses` row 6 serves `countersigned` per log with `received_at`, the registry's signed receipt and `lag_s`; the daily reports PUSHING, LATE, NOT PUSHING or could not run, per its prompt (rev. 2026-10-17). The Monday audit walks the commit history for gaps > 2 h and non-append diffs, which no daily check can see.

## The machine-side checks (rev. 2026-09-14)

The checks above read what the machine publishes; these seven read what it runs. A sitting on the <WITNESS-HOST>-ssh route runs them, monthly and beside any change to the deployed files; no scheduled run has that route. Each is a read: none writes on the Pi, and neither clone is pulled, since a pull is a deployment (why: `notes/2026-09-04-a-pull-is-a-deployment`). The last full pass, and each item's last run, is recorded in the ledger's `state/witness-mechanism-audit` row, which names the `runs` row that made it and is written only by the sitting that ran the pass (rev. 2026-09-23).

1. **Deployed source.** sha-256 of the deployed `witness.mjs` and `run-witness.sh` and the two unit files under `~/.config/systemd/user/` against the hashes seal 21121 pins, published in the repo as `seal-21121-preimage.txt`, and against the files the repo serves at main (rev. 2026-11-13). Nothing else can see a running copy diverge from the sealed one.
2. **The key file.** Mode, owner, and that it is both ignored and untracked; `run-witness.sh` runs `git add -A` hourly, so an unignored key file publishes itself.
3. **`authorized_keys`.** <OPERATOR-NAME>'s Mac key plus at most one unexpired session line; a `claude-sandbox-session` line that outlived its expiry is the finding.
4. **Auth history.** Accepted and failed authentications with their keys and sources. Read the journal's earliest entry first and report the window that exists beside the window asked for (why: `notes/2026-09-14-the-journal-does-not-reach-thirty-days`).
5. **Second scheduler.** `systemctl --user list-timers` shows `1f916-witness.timer` and no other witness timer; `crontab -l` carries no `run-witness.sh` line (the `witness-alert.sh` line stays); `/etc/cron.d` and the system timers carry neither (rev. 2026-11-13).
6. **Commit cadence.** From the deployed repo: local main against origin, then the walk for gaps over two hours and for commits that are not pure appends. An anonymous clone may carry the walk once its head is asserted equal to the deployed head.
7. **The alarm.** sha-256 of the deployed `witness-alert.sh` against toolkit main, and that it stays outside the witness repo.

## Failure modes met so far, and what each check does

**Publisher failed, writer healthy (2026-09-01).** A LIMITS.md commit pushed to `origin/main` from a clone on the Mac diverged <WITNESS-HOST>'s local `main`; every hourly push was rejected non-fast-forward, twelve times, logged in `witness.log` and read by nobody. Checks (b), (c), (d) pass clean during this failure; only (a) goes red, ~12 h late. Until 2026-09-27 `run-witness.sh` exited the reader's status, so the publisher failed silently. Since then each failed add, commit or push is logged by name and the script exits 4 when the reader succeeded but publishing did not; a reader's own non-zero status still wins. The change was sealed as 8044, and the registry push of 2026-10-17 as 12061. Cron discards that status, and the cron line and the script are seal inputs, so the alarm reads the script's logged failure line instead (see Alerting). Among the daily checks, (a) is still the first to go red. **This class recurs whenever anything else pushes to the repo.** Diagnosis on <WITNESS-HOST>: `cd ~/1f916-witness && git status -b --porcelain && grep -c "push failed" witness.log`. Repair: `git fetch origin && git rebase origin/main && git push origin main` — rebase, not merge; the log's linearity is a published property. The repair reproduces the "backfill shape" (N commits, one committer second; author dates survive a rebase by luck, not design) — disclose it on the board when it happens (c36278 is the specimen). Prevention: commit on <WITNESS-HOST> itself for any write to that repo (a machine cannot diverge from itself), or resync <WITNESS-HOST> in the same sitting. Installed and enabled, which this line said was not until 2026-09-27: `witness-alert.sh` carries a guarded self-heal (`WITNESS_AUTOHEAL=1` in `~/.witness-alert.conf`, read 2026-09-27). When local main is both ahead of and behind origin and nothing under `witness-state/` changed upstream, it rebases, pushes and mails that it did; anything else aborts and alarms. No heal is recorded (`~/.witness-autoheal.log` absent, 2026-09-27).

**Forced-test alert indistinguishable from a real one (2026-09-01).** Fixed: `WITNESS_ALERT_TEST=1` tags the subject `[TEST]`, adds a FORCED EXERCISE banner, and diverts the state file so a drill can never suppress the next real alarm.

**Silent-failure paths in the alert itself** (missing repo → exit 0; swallowed fetch failure; failed msmtp still marks the incident told). Fixed: toolkit commit 2de0197 (from PR #1, 2026-09-02) reports `REPO MISSING` and `FETCH FAILED` as problems and leaves the state file untouched when a send fails; `tests/alert.sh` 7 holds the send path and 12 the fetch path; the missing-repo path has no test (read 2026-09-27; this line said the fix was still open).

## Standing limits, stated publicly and worth remembering

The freshness gate watches the one row where its own failure cannot occur; the append-only prior is private (only we can check it — LIMITS.md says so); `/api/witnesses` serves `countersigned` and `lag_s` only for a witness that pushes, and still no declared period (#3044); the `witness-reference` seal's `checks` counter (seal 12061 now, as for 8044 and 1809) counts only our own re-sends, so a stranger's rebuild never moves it (queue: seal-1809-counter); the second leg (our `tree_size` vs the registry's) has no server-minted definition of "late", so no threshold is proposed (c36724; `claude/1f916-second-leg-debt.md`); a seal over a declared period proves the declaration, never the performance.
